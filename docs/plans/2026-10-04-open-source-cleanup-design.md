# 开源项目整理设计

日期：2026-10-04
项目定位：企业 AI 业务接入平台

## 目标

将仓库从内部研发交付形态整理为可公开阅读、可本地复现、可持续贡献的开源项目。公开首页应该让第一次访问者在几分钟内理解平台解决的问题、核心边界和运行方式；内部部署记录、客户账号、生产地址和历史排障细节不应出现在公开文档中。

## 方案选择

### 方案 A：只删除 `docs/roadmap.md`（不推荐）

改动最小，但会留下 README、协作规范和方案文档中的大量失效链接，也会丢失仍有价值的架构和验收边界。开源访客无法判断项目当前能做什么，维护者也没有公开的后续计划。

### 方案 B：保留原路线图并改名（不推荐）

可以避免链接断裂，但 148 KB 的内部实施日志仍然会暴露生产部署拓扑、测试账号命名和历史决策上下文。它适合内部仓库，不适合作为开源项目的公共入口。

### 方案 C：公开文档重组，归档内部细节（推荐）

将根目录路线图替换为精简的 `docs/roadmap.md`，把长期有效的架构说明整理到 `docs/architecture/`，把 MCP/ADP 接入说明整理到 `docs/integrations/`，把运行和发布说明保留在 `docs/operations/` 并删除环境特有信息。README 只承担项目首页职责，贡献、安全和行为规范独立成文件。旧路线图从工作树移除，历史仍可通过 Git 提交记录追溯。

## 公开信息边界

- 保留：模块职责、API/MCP 契约、环境变量名称、迁移命令、测试命令、Mock 的使用边界和未完成能力。
- 删除：生产域名、服务器别名和路径、真实部署版本、客户/测试账号、手机号、内部备份路径、内部工单和具体凭据状态。
- 示例数据使用明显的占位符；示例凭据只写变量名，不写可用值。
- 真实第三方联调状态使用“需要外部账号和权限”描述，不能用本地 Mock 或单测替代。

## 文档信息架构

```text
README.md                       项目首页和快速开始
CONTRIBUTING.md                 开发、提交、PR 和测试约定
CODE_OF_CONDUCT.md              社区行为规范
SECURITY.md                     漏洞报告和密钥处理
docs/
  roadmap.md                    精简公开路线图
  architecture/overview.md      平台边界和模块架构
  integrations/mcp-and-adp.md   MCP、ADP 和工具接入
  development.md                本地开发和验证
  operations/                   通用运维、备份和排障
  plans/                        可复用的设计决策和历史方案
```

## 验收标准

1. 根目录不存在 `ROADMAP.md`，README 和协作规范只引用 `docs/roadmap.md`。
2. README 能独立说明定位、架构、快速开始、配置、测试、限制、贡献和许可证。
3. 当前跟踪文件不包含生产域名、服务器路径、客户账号、手机号、真实 Token 或密码。
4. 文档中的本地命令与当前目录结构一致，迁移 revision 使用代码中的当前版本。
5. `make platform_api_check`、后端定向测试、前端类型检查/构建、Markdown 链接检查和 `git diff --check` 通过。
