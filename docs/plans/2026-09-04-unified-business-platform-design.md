## 1. 方案结论

推荐在现有项目上渐进重构为“模块化单体业务平台”：复用聊天组件和 ADP 协议适配，重新建立统一身份、企业数据范围、渠道消息、业务工具和可视化管理能力。

部署初期是一套代码、一个数据库，按职责启动 API 和 Worker 两个进程；不是给每个模块部署一个微服务。

职责分工：

- 自研平台：用户身份、企业归属、权限、渠道绑定、会话归属、消息收发、业务工具、证据校验、审计和运营配置。
- ADP：自然语言理解、应用内的智能体编排、工具选择、语言组织。
- M3：真实订单、提单、船名、航次和船期等业务数据的权威来源。
- 渠道平台：提供经过验证的渠道身份和消息收发能力，不负责决定用户可以查看哪些 M3 数据。
- 管理后台：管理自研平台，不在第一期重新制作一套 ADP 智能体编排画布。

关键边界：业务身份不交给模型判断，业务权限不靠提示词保障，平台与 M3 密钥不暴露给浏览器或模型。

## 2. 已确认范围与设计假设

### 2.1 已确认需求

1. 一家货代公司运营，客户企业预计不超过 1,000 家；这不等于同时在线人数不超过 1,000。
2. 先录入客户企业，再录入该企业的员工账号。
3. 手机号作为平台登录的业务唯一索引；内部使用不可变 user_id 关联数据。
4. M3 客户编码绑定企业，不绑定某个员工；不使用备注字段代替企业关系。
5. 客户由客服、销售或有权限的管理员开通，没有自助注册。
6. 初始密码为随机 6 位口令，无短信依赖，暂不提供用户自行修改密码；管理员可重置。
7. 客户可从官网、微信服务号、微信客服、企业微信等入口查询。
8. 第一期 M3 业务只读；内部人员可以在管理后台维护平台账号、权限和配置。
9. 没有数据或无法核实时明确说明，不编造业务事实。

### 2.2 本稿采用的默认方案

- 先做单货代企业部署，不做面向多家货代公司的 SaaS 租户计费系统。
- 客户用户默认归属一家客户企业；货代内部员工归属运营组织，另行分配可服务的客户企业范围。
- 默认客户员工可查询本企业授权业务，但不能查看同企业其他员工的聊天记录。
- 同账号跨渠道共用业务权限，各渠道的聊天上下文默认独立。
- 客户业务查询优先单聊；群聊不直接输出私有订单详情，提示转入受控单聊。
- 内部运维机器人第一期仅支持查看状态、查看脱敏错误、生成排障建议；自主改代码、执行命令、部署和修改数据库不纳入本期。
- M3 文档、测试账号、数据归属字段和 API 限额尚待提供；本文工具名是平台拟定义的语义工具，不是已核实的 M3 接口名称。

## 4. 重构路径与关键决策

### 4.1 三种路径

| 路径 | 优点 | 代价 | 结论 |
|---|---|---|---|
| 原项目上渐进模块化 | 保留已跑通的聊天和部署链路；变更可分步验证 | 需要梳理旧接口并保留短期兼容层 | 推荐 |
| 只保留聊天组件，后端整体重写 | 新结构更统一 | 丢失现有调试成果，迁移和回归范围更大 | 团队有明确技术栈约束时再考虑 |
| 直接拆分多个微服务 | 可独立扩容、独立发布 | 身份传播、配置、部署、观测和排障成本显著增加 | 当前规模不采用 |

### 4.2 提议 ADR

所有决策状态均为 Proposed，评审后再固化为独立 ADR。

| ADR | 背景与决策 | 收益 | 代价与替代方案 |
|---|---|---|---|
| ADR-001 模块化单体 | 现有 Python/Sanic、Vue 可工作，先保留技术栈并明确模块边界 | 避免框架迁移和业务重构同时发生 | 后续独立扩容前需要提取模块；不选立即微服务化 |
| ADR-002 平台掌握身份和会话 | 多渠道必须共享授权规则，统一业务消息先到自己的后端 | 可控制绑定、封禁、数据范围和审计 | 需要承担渠道协议维护；不选私有业务渠道直接绕过平台连接 ADP |
| ADR-003 保留 ADP 编排 | 已有应用可聊天，将 ADP 封装为 AgentProvider | 可复用当前智能体并保留替换入口 | 不承诺不同平台的工作流可无成本迁移；不同时引入第二套 Agent 框架 |
| ADR-004 PostgreSQL 为主库 | 企业、用户、授权、消息需要关系与事务 | 利用现有基础，减少组件 | 初期数据库任务队列吞吐有限；达到压测边界后再拆 Redis/专用队列 |
| ADR-005 业务查询证据化输出 | 客户要求不编造船期和状态 | 关键字段直接取自已授权的真实工具结果 | 业务结果不原样逐 token 展示，牺牲部分流式体验换取可校验性 |
| ADR-006 管理与业务运行分权 | 客户聊天不应等于云 API 管理权限 | 降低配置误改、跨客户访问风险 | 需要独立权限配置；不保留用户侧任意 ADP Action 转发 |

## 6. 多渠道接入

### 6.1 接入原则

对私有业务查询，推荐“渠道直接接入自研后端，再由后端调用 ADP 对话 API”。

仅把域名反向代理到 ADP，不代表本平台已经掌握发送者身份或实施鉴权。要自主鉴权，就需要真正处理渠道协议和消息生命周期，而不是只做 URL 转发。

腾讯云的原生发布渠道可以保留用于独立的公开问答演示；不要与同一生产机器人同时争抢消息入口。

官方目前说明企微机器人既有长连接也有 URL 回调；两种方式不可同时有效，同一机器人只能保持一个有效长连接。自研方案需要自行实现相应协议，不能把“由 ADP 建立连接”当成“由自研平台建立连接”。参考：[企微智能机器人发布说明](https://cloud.tencent.com/document/product/1759/121473)。

### 6.2 渠道设计表

渠道实例属于平台，不属于企业。平台管理员配置渠道协议参数和凭据时不选择企业；渠道实例只定义消息如何安全进入和离开平台，不携带业务数据授权。渠道身份同样只关联平台用户，不预先固化企业。消息进入后，Worker 按用户当前有效 membership、企业范围、功能权限和字段权限创建受控执行上下文，校验通过后才转发给一期全平台唯一的 ADP 应用；只有一个有效企业时可自动选择，存在多个有效企业且消息没有可信企业范围时必须拒绝执行并要求明确范围。

一期 ADP 应用也不与企业绑定。其运行配置由服务器环境中的 `TC_SECRET_APPID`、`TC_SECRET_ID`、`TC_SECRET_KEY` 和 `APP_CONFIGS` 提供；企业归属是每次消息执行上下文的授权属性，不是 ADP 应用或渠道配置属性。历史 `IntegrationConnection` 与 `EnterpriseExternalAccount` 仅保留给旧兼容路由，不能作为新平台渠道的配置前置条件。

下列身份字段为拟对接模型；确切字段、可见范围及账号条件需用客户实际账号的回调样本验证，不假定能获取手机号。

| 渠道 | 接入方式 | 身份映射键 | 回复策略 |
|---|---|---|---|
| 官网 | HTTPS API，结果通过 SSE/查询接口返回 | 平台登录会话 -> user_id | 进度可流式，关键业务结论校验后返回 |
| 微信服务号 | 自有服务处理平台消息/事件回调 | 服务号实例命名空间 + OpenID | 按账号实际权限与消息窗口回复；超时或不具备发送能力时提供官网查询入口 |
| 微信客服 | 自有服务接收通知，再按客服协议同步消息 | 企业/客服渠道实例命名空间 + external_userid | 保存同步游标、消息去重、按客服回复窗口发送 |
| 企微智能机器人 | 自有 Worker 长连接，或自有 HTTPS 回调；选择一种 | 企业与机器人实例命名空间 + 发送者标识 | 遵守机器人协议的流式/更新和时间限制；失败时提示重新查询 |

微信服务号和微信客服是不同产品，分别配置凭据、接收协议和身份映射，不能把两个账号体系里的 ID 当成同一个用户。

微信客服的原生 ADP 发布方案有独立的回调和凭据配置，不能由该方案推导出任意自建鉴权步骤已经存在。参考：[微信客服发布说明](https://cloud.tencent.com/document/product/1759/122567)。

官网和微信服务号首先面向外部客户。企微智能机器人优先面向货代内部员工；外部客户能否在目标企微形态中使用机器人，必须由客户账号和平台实际能力验证，不能默认“所有微信客户都能访问企微内部机器人”。

### 6.3 标准消息契约

适配层输出统一 InboundMessage，至少包含：

- channel_instance_id、external_message_id、external_conversation_id。
- sender_identity_id、recipient/room 信息、message_type、text、received_at。
- trace_id、协议版本、可用回复方式与回复截止时间。
- 经过验签/解密的来源证明；原始载荷默认不全量落日志。

随后 identity/access 模块生成 TrustedContext：

- user_id、enterprise_id、account_type。
- 当前有效权限、可服务企业范围、策略版本。
- channel_instance_id、conversation_id、run_id、认证有效期。

身份上下文由服务端生成；适配器不能从消息正文中的“我是某某客户”生成可信身份。浏览器也不能指定企业、权限或任意供应商会话 ID。

## 7. 企业、账号、绑定与会话隔离

### 7.1 开通服务流程

    销售/客服录入企业
      -> 关联 M3 客户编码并校验
      -> 创建该企业员工账号，录入手机号
      -> 分配初始密码与角色
      -> 通过既有人工渠道交付
      -> 客户登录官网，或完成渠道身份绑定
      -> 在授权范围查询

手机号做规范化后唯一约束，内部主键使用 UUID。换手机号不应改变用户主键或导致历史会话串号。

企业与 M3 账号采用映射表，第一期可限制每个 M3 连接下一个企业对应一个客户编码；未来支持一个企业多个编码不必改用户模型。映射的变更必须有权限、记录审计，并使相关授权缓存失效。

### 7.2 绑定不是永久授权

- 未绑定：提醒联系销售/客服；可发起绑定申请，但不能仅凭自报企业名称获得访问权。
- 绑定方式优先使用平台 HTTPS 登录/绑定页，手机号加平台密码验证；不引入短信。
- 页面使用短期一次性 state，并绑定到发起渠道身份；如果可用则校验渠道 OAuth 身份。
- 无法取得页面侧渠道身份时，完成登录后还需在原渠道由原发送者确认，不能仅凭打开一条可转发链接就绑定成功。
- 若采用聊天内输入口令，必须由专用认证流程截获，不送入 ADP、不进普通聊天记录；默认推荐登录页，减少口令进入聊天平台历史。
- 已绑定只代表平台知道这个渠道身份对应哪个平台用户，不代表已经授予或固化任何企业数据范围；是否可以查询还取决于执行时的身份有效性、账号状态、有效 membership、企业状态和业务权限。
- 这里的“执行时鉴权”不等于“必须存在浏览器登录会话”。官网消息由其登录会话授权并随会话失效；渠道消息由已确认的渠道身份加执行时 membership/权限版本授权，执行上下文不关联登录会话。要求渠道消息也持有有效网页登录态会让已绑定但未登录官网的客户无法提问，也会让渠道消息借用无关的浏览器会话。账号停用、密码重置和解绑必须同时作废两类执行上下文与待发送结果。
- 管理员重置密码、停用账号或解绑后，旧网页登录态和渠道身份应失效；企业停用、membership 或角色变化不删除平台用户级渠道身份，但必须让旧执行上下文和待发送私有结果立即失效，并在下一次消息执行时按最新范围重新鉴权。

遵循已确认的 6 位初始口令方案，但需要随机生成、安全哈希保存、账号与来源组合限流、失败锁定和审计。初步建议连续失败 5 次暂时锁定 15 分钟，具体值在试运行中调整。短口令的固有风险仍然存在；平台管理员另用强密码，不能与客户共用 6 位运维密码。

### 7.3 会话模型

- 一个用户可有多个渠道身份。
- 同一用户的微信、官网、企微会话默认彼此独立；统一的是账号和数据权限，不是自动拼接所有聊天。
- 同企业员工共享授权业务范围，不共享个人会话。
- 平台生成 conversation_id，并持久保存到对应 ADP application/visitor/conversation 的映射。
- ADP VisitorId 使用稳定的不透明平台标识，不使用姓名、手机号或企业名；多个权限域需要不同访客命名空间。
- 读取、续聊、导出、删除、分享、补发全部检查归属，不只检查“有没有登录”。
- 解绑、转企业、收窄权限时关闭或轮换相关供应商会话，避免旧上下文在后续回答中泄露已撤销范围的数据。
- 第一期开关默认关闭对外分享私有业务会话；原项目的公开分享功能不能原样开放。

## 8. 权限模型与 M3 工具网关

### 8.1 授权判断

授权 = 身份有效 + 功能权限 + 企业范围 + 字段权限 + 当前渠道与会话条件。

建议固定角色模板起步，支持管理员调整权限集合；第一期不做复杂策略语言和可视化规则编程器。

| 角色 | M3 业务查询 | 平台配置 | 数据范围 |
|---|---|---|---|
| 未登录访客 | 不允许 | 不允许 | 仅公开 FAQ |
| 客户员工 | 已授权的只读工具 | 不允许 | 本企业允许的记录和字段 |
| 销售/客服 | 已授权的只读工具 | 按授权开通和绑定客户账号 | 被分配的客户企业 |
| 业务主管 | 已授权的只读工具 | 分配业务范围，按授权管理客户 | 所负责团队/企业 |
| 平台管理员 | 不因管理员身份自动获得全部业务数据 | 用户、角色、渠道、Agent 和工具配置 | M3 数据权限另外授权 |
| 运维人员/运维机器人 | 默认不开放 M3 客户数据 | 状态、脱敏日志、受控诊断 | 最小必要范围 |

客户能登录不等于能访问所有 ADP 应用。平台后台管理员也不等于腾讯云账号管理员。

### 8.2 工具与 M3 API 的关系

工具网关不只是 ADP 连接器包装，它负责：

1. 隐藏 M3 私有协议、凭据和真实接口地址。
2. 将业务意图映射到一个或多个已批准 M3 接口。
3. 校验输入、强制范围、裁剪输出字段。
4. 统一错误、超时、重试、限流和调用审计。
5. 为 ADP 或未来其他 Agent 提供稳定工具契约。

拟定义的只读语义工具，例如：

| 平台工具 | 功能权限 | 模型可以提供 | 服务器必须决定 |
|---|---|---|---|
| shipment.lookup | shipment.read | 提单号、柜号及必要澄清信息 | M3 连接、允许的客户编码、输出字段 |
| shipment.schedule | schedule.read | 已授权业务标识 | 实体归属、船期字段映射、查询范围 |
| shipment.milestones | milestone.read | 已授权业务标识 | 可读取节点及状态解释 |

最终是否拆成三个工具，取决于 M3 文档；不为了架构形式重复调用同一个上游接口。

每个工具在代码中登记名称、版本、输入/输出 Schema、所需权限、允许的上游动作、超时预算和审计策略。后台只能启停已登记工具和配置授权，不允许普通管理员输入任意 URL、SQL 或脚本形成工具。

M3 只读按业务语义判断，不按 GET/POST 方法判断；查询接口也可能使用 POST。第一期写入类接口不进入允许清单。

### 8.3 请求范围防护

- 优先把允许的客户编码作为 M3 查询条件，阻止越权数据被拉取。
- 对返回记录再次检查企业归属，再做字段白名单；仅将通过授权的最少必要字段交给 ADP。
- M3 不支持范围过滤时，需要验证其返回内容能否可靠判断归属，并限制网关内部可见性。
- 如果既不能按客户范围查询，也没有可信归属字段，则该工具不能开放给客户，必须先补齐上游能力。
- 查询到别人的记录和记录不存在，对客户统一返回“未找到可访问的业务记录”，避免泄露记录是否存在。
- 审计内部区分无记录、越权、超时、上游错误，便于排查。

### 8.4 身份如何随 ADP 工具调用传递

不能把 user_id 或 customer_code 写进提示词就视为鉴权完成。

推荐流程：

1. 平台验证来访者，创建本轮 run_id。
2. 生成高熵、短期、不透明的 context_token，服务端记录它对应的用户、企业、权限版本、Agent 应用、渠道、会话和允许工具。
3. 由后端通过 ADP API 参数注入，工具参数固定引用该变量并设为模型不可见；普通客户端不可写入此字段。
4. ADP 调用业务工具时同时使用受控的服务身份凭据和 context_token。
5. 工具网关验证调用者、上下文有效期、应用及运行绑定，并重新检查当前用户状态和权限，再执行工具。
6. 本轮完成或取消后撤销上下文；过期、缺失、跨应用和跨会话使用一律拒绝。合法的多工具调用和重试通过 tool_call_id 幂等处理，不把令牌错误地限定为只能调用一次。
7. 该令牌仍按敏感凭据管理：不展示给用户，不写日志，不送给无关第三方工具。

腾讯云文档描述了通过 API 参数变量配置工具参数、并关闭模型可见性的方式。这里采用该能力传递受控上下文，但是否在客户当前应用模式、新版对话协议和具体工具类型中完整支持，需要在首个技术验证里确认。参考：[使用工具](https://cloud.tencent.com/document/product/1759/117856)。

如果验证失败，禁止退化为信任模型提供的 user_id。安全替代方案是在自研编排层执行授权后的工具，再把最小结果送给 ADP 组织语言；这会增加自研编排工作量，需要明确调整范围。

## 9. 真实数据回答与防编造

仅使用“不要编造”的提示词不足以满足要求，第一期针对有限业务字段采用可验证输出。

- 工具返回统一结果：状态、结构化数据、来源 M3、查询时间、源数据更新时间、证据 ID。
- 工具状态至少区分成功、无可访问记录、字段未知、需澄清、上游暂不可用。
- 开船时间必须区分预计与实际；到港时间区分 ETA 与实际到港；无字段值不推断。
- 如果一个提单对应多个柜、航段或运输任务，先澄清或分别展示，不能随意取第一条记录。
- 订单状态与运输节点分别解释，映射表需要业务人员确认。
- 关键业务字段由模板/卡片直接渲染自工具证据，不由模型自由填写。
- ADP 可识别意图、选择工具、提出澄清问题、整理解释；如生成含业务断言的文本，需与证据做结构化校验，失败就回退确定性模板。
- 私有业务回答不直接把 ADP 原始 token 流转发给用户。可以流式展示“正在查询”等进度，最终内容通过校验后才发送。
- 未调用真实工具、工具失败或无证据时，禁止回答具体订单状态、船期和费用。
- 公开常识问答与私有业务问答分开配置；公开访客使用无 M3 工具、无私有记忆的独立应用或受控流程。
- 默认不对客户展示模型思考过程、工具原始载荷、认证上下文或内部日志。
- 历史对话中的旧船期不能充当本次查询的最新证据。第一期不缓存业务结果；后续缓存必须带企业/权限范围、来源时间和明确的过期提示。

## 10. 可视化管理后台

新增独立管理端，不把客户聊天页的“设置”扩展成所有人的万能入口。

    管理后台
    ├── 总览：调用量、成功率、超时、待处理失败
    ├── 客户企业：企业资料、M3 编码、状态、负责员工
    ├── 平台用户：手机号、所属企业、角色、初始口令/重置、停用
    ├── 身份绑定：渠道身份、绑定申请、确认、解绑、授权到期
    ├── 权限管理：角色模板、工具权限、企业范围、字段范围
    ├── 渠道管理：官网/服务号/微信客服/企微实例、接入参数、健康状态
    ├── Agent 配置：应用绑定、服务商、路由、预算、功能启停
    ├── 业务工具：已登记工具、版本、可用角色、超时、测试连接
    ├── 会话与调用：授权范围内的记录、证据、trace_id、错误定位
    └── 系统与审计：配置版本、密钥轮换状态、操作记录、失败任务

后台的重点流程：

1. 新建企业 -> 验证 M3 客户映射 -> 新建用户 -> 交付初始口令。
2. 新建渠道 -> 完成平台侧配置 -> 验证消息接收 -> 绑定测试用户 -> 测试回复 -> 启用。
3. 配置业务工具 -> 测试正常与越权案例 -> 关联角色 -> 发布配置。
4. 查看失败执行 -> 区分接收/ADP/工具/回复哪一步失败 -> 按规则重试或联系客户。

配置采取“草稿 -> 校验 -> 发布 -> 可回滚”的轻量版本机制。第一期不做复杂审批流；变更人、时间、版本和影响对象必须可追溯。

密钥字段采用只写、掩码显示，不提供查看明文按钮；测试连接也不返回密钥。业务审计与普通诊断日志分开，查看聊天正文和导出需要单独权限。

后台不复制 ADP 的模型市场、知识库编辑器和工作流画布。第一期提供应用绑定、运行参数、可用能力与跳转入口；是否通过云 API 管理更多内容以后单独评估。

## 11. 数据设计范围

在正式 Schema 中落地以下实体；本稿先确定边界，不直接生成迁移 SQL。

| 数据组 | 主要实体 |
|---|---|
| 企业与成员 | enterprises、users、enterprise_memberships、staff_enterprise_scopes |
| M3 映射 | integration_connections、enterprise_external_accounts |
| 认证 | password_credentials、auth_sessions、channel_auth_grants |
| 角色权限 | roles、permissions、user_roles、role_permissions、角色/用户业务范围 |
| 渠道身份 | channel_instances、channel_identities、identity_bindings、binding_requests |
| 智能体与工具 | agent_profiles、agent_routes、tool_definitions、tool_grants |
| 会话执行 | conversations、conversation_participants、provider_conversations、messages、agent_runs、tool_calls |
| 可靠投递 | inbound_events、delivery_jobs、outbound_messages、channel_sync_cursors |
| 配置与审计 | config_versions、secret_references、audit_events |

约束要求：

- users.phone_normalized 唯一；内部关联始终使用 user_id。
- 第一期对客户用户限制一个有效企业成员关系；内部员工的客户范围通过独立关系表达。
- 渠道身份按命名空间唯一，至少包括渠道实例和外部身份；不能只对 OpenID 全局唯一。
- 一个渠道身份同时只能绑定一个有效平台用户，一个平台用户可绑定多个渠道身份。
- 渠道身份不保存授权企业；历史 `EnterpriseId` 仅为 nullable 兼容字段，新记录固定为空，企业范围在 Worker 执行时解析。
- M3 编码唯一性至少在 integration_connection 内约束；企业关系用外键，不用备注。
- 平台会话与供应商会话明确映射，访问时同时校验用户、企业、渠道和应用。
- 入站消息以渠道实例加协议消息唯一键去重；没有消息 ID 的事件按协议定义构造稳定键。
- 每条出站消息记录 run_id、目标渠道、目标身份、幂等键、发送状态和上游消息 ID。
- 业务数据不全量同步进平台，只保存必要的最小查询证据或脱敏摘要；证据正文加密、限期保留。
- 聊天正文、审计、错误摘要分别设置保留期；先建议正文 30 天、安全审计 180 天，需按客户合同和实际合规要求确认。
- 日志、导出、分享、缓存和失败任务同样带数据范围约束。

## 13. 消息可靠性、异常处理与部署

### 13.1 为什么增加 Worker

模型和 M3 查询可能比渠道回调等待时间长。回调入口不能一直等待 AI 回答。

基本流程：

    接收并验证 -> 事务写入消息与任务 -> 按协议确认接收
                                     |
                                   Worker
                                     |
                             ADP + 受控工具
                                     |
                        证据校验 -> 写入待发回复
                                     |
                       渠道发送 -> 更新投递状态

- 接收确认、机器人流式更新和最终回复均按各渠道协议处理；不能给所有渠道套用同一种“返回 200 后再回复”实现。
- 基于 PostgreSQL 做轻量持久任务、租约、重试计数与失败列表；同一会话串行执行，不同会话可并发。
- 长耗时模型调用不保持数据库长事务；任务领取、执行和完成分别处理。
- 进程重启后恢复未完成任务；不把内存中的后台协程当成可靠消息队列。
- 区分“业务执行重试”和“发送重试”。回复发送失败时优先重发已校验结果，不重复调用模型/M3。
- 不宣称跨平台 exactly-once；若外部平台已接收但本地未确认，使用上游消息 ID/状态查询去重；无法确认时标记投递状态不确定，不盲目无限重发。
- 本轮无权、参数错误、凭据错误不自动重试；超时和短暂服务故障才有限重试。
- 重试前复核用户/企业状态；禁用后不得继续发送排队中的私有业务数据。
- 同一机器人长连接设单实例所有权和租约；扩容不能启动多个进程抢同一个连接。
- 取消、超时、权限撤销后关闭本轮上下文和上游生成，记录确定的终态。
- 人工接管第一期可采用“暂停该会话 AI + 联系销售/客服入口”，不承诺跨渠道统一客服坐席系统。

### 13.2 部署建议

初期腾讯云 CVM + Docker Compose，四个逻辑运行单元：

| 单元 | 作用 |
|---|---|
| reverse-proxy | HTTPS、静态客户/管理页面、路由、请求限制 |
| api | 登录、后台 API、渠道接收、业务工具入口 |
| worker | 异步执行、渠道连接、回复、重试 |
| postgres | 业务配置、权限、会话、任务与审计 |

API 与 Worker 使用同一镜像、不同启动命令。数据库可本机容器化用于 POC；生产可迁移托管 PostgreSQL以降低备份维护负担。

Redis 暂非必需；只有压测证明数据库队列/限流成为瓶颈，或需要多机高吞吐时再增加。首期不引入 Kubernetes、Kafka、Elasticsearch、向量数据库或自建 GPU。

公网只暴露必要 HTTPS 入口；数据库不暴露公网。ADP 云端调用工具需能访问受控 HTTPS 地址，因此工具入口不能只绑定容器内网，也不能靠“路径难猜”保护，必须做服务身份鉴别与运行上下文校验。

### 13.3 最小运维能力

- 分别监控渠道接收、身份认证、ADP 聊天、ADP 管理接口、M3、出站投递。
- trace_id 串联消息、run、工具调用、证据和最终回复；记录耗时和错误分类，不记录口令、AppKey、Token。
- 密钥加密存储，主密钥通过部署环境/挂载秘密注入，与数据库分离；后续可接腾讯云密钥管理服务。
- 开发、测试、生产分离应用与凭据；客户真实数据不进入演示环境。
- 配置 AppKey、M3 Token、渠道 Token 时只允许使用批准的目标域名，防止后台测试接口被用作任意网络代理。
- 数据库备份、异地/独立介质保存、恢复演练；只备份到同一 CVM 不算抵御整机故障。
- POC 单 CVM 有单点风险，不承诺生产高可用 SLA。
- 初步容量目标建议从 20 个并发查询执行测试，服务端自身普通接口 p95 小于 500ms；端到端时延需单独测量 ADP 与 M3，不把建议值当成已达指标。
- POC 暂按每日备份设计，意味着 RPO 最坏可能接近 24 小时；若要更小 RPO，需连续备份或托管方案。RTO 在恢复演练后确认。
- 密钥泄露、越权尝试、连续查询失败和渠道积压设置可操作告警。

## 14. 分期实施与验收

### M0：技术验证与风险收敛

交付：验证记录、M3 字段清单、权限映射草案、渠道账号能力清单。

- 取得 M3 文档、测试权限与至少两家企业的隔离测试数据。
- 验证 ADP 当前应用模式与协议中的隐藏运行参数传递、工具回调鉴别、结构化结果。
- 验证客户实际渠道发送者标识、消息回复窗口、回调验证/长连接模式和账号权限。
- 排查当前 ADP 管理 API 元信息报错；与已可用聊天分开处理。
- 确认只读权限与记录归属检查可实现；失败时先解决，不以提示词代替。

### M1：业务底座与可用后台

交付：企业/用户/角色/绑定/配置后台，认证 API，数据库迁移，基础审计。

- 管理员先建企业再建用户，能重置密码、停用、配置企业范围。
- 官网客户登录走新身份服务。
- 客户不能访问任何管理 API；旧路径不能绕过权限。
- 初始口令不会进入聊天、模型或诊断日志。

### M2：官网 + M3 完整只读闭环

交付：可用查询、受控工具、证据化回复、会话隔离与测试报告。

- 真实 M3 查询成功，能解释预计/实际船期。
- 无记录、未知字段、多记录、上游失败均有明确反馈。
- A 企业无法查询 B 企业；同企业员工无法读彼此会话。
- 停用用户后旧会话、旧上下文和待发送任务不可继续返回私有数据。

M1 与 M2 构成第一个可交付业务版本，而不只是一个能聊天的演示。

### M3：多渠道接入

交付：微信服务号、微信客服、企微适配器及后台配置和联调记录；按实际优先级逐个上线。

- 多渠道身份映射到正确平台账号，同一企业数据范围一致。
- 同账号不同渠道上下文隔离；频道/群聊不泄露私有数据。
- 重复消息、断线重连、超时、进程重启、发送失败均可追溯。
- 微信侧凭据及域名等准备情况决定联调开始时间，不能只按代码完成时间承诺交付。

### M4：试运行与交付

交付：Docker 部署、OpenAPI、数据字典、运维手册、备份恢复记录、账号开通 SOP、验收用例与培训。账号开通、口令交付、范围确认、停用/重置和验收记录模板见 `docs/operations/account-onboarding-and-acceptance.md`。

- 压测与容量记录。
- 日志/密钥脱敏和权限回归测试（本地专项已完成，生产日志管道和第三方联调仍待外部验收）。
- 运维机器人只读状态入口；自主开发部署作为另一个受控阶段评估。
- 版本发布、回滚和数据库迁移演练。

目前不承诺精确工期。估算需要明确 M3 API 质量、渠道数量与账号可用性、后台页面深度和投入人力；M0 结束后以验收模块估算，不以“1,000 家客户”直接推导开发成本。

## 15. 必须覆盖的测试

1. 同角色不同企业、同企业不同用户、同用户不同渠道的隔离测试。
2. 伪造 enterprise_id、user_id、ApplicationId、ConversationId、IsChannel、CustomVariables 时被拒绝或忽略。
3. ADP 工具请求缺少上下文、过期、跨应用、重放和撤销后调用被拒绝。
4. M3 返回无归属记录、多企业混合记录、缺字段、未知状态和多航段时安全处理。
5. 用户在问题中要求绕过权限、工具返回文本包含恶意指令时，授权与字段过滤不受影响。
6. 客户隐藏管理按钮之外，直接调用管理 API 也被拒绝。
7. 服务重启、重复回调、队列租约过期、消息发送结果不确定时不发生失控重试。
8. 账号停用、企业映射变更、角色收窄、密码重置后授权即时失效；供应商旧上下文不会越权复用。
9. ADP 聊天正常但元信息失败时，聊天按能力降级，不显示笼统“全部不可用”。
10. 回复中的船名、航次、时间和状态能映射到本轮真实证据；未知值不会被模型补齐。

测试分为单元测试、适配器契约测试、测试数据库集成测试和真实浏览器/渠道验收。第三方真实账号测试与 Mock 测试明确标记，不能用模拟数据通过来证明 M3 已接通。

## 16. AI 辅助开发约束

- 模块职责、输入/输出契约、权限表和 ADR 入库，避免靠聊天记录传承设计。
- 关键接口用类型与 Schema 约束；生成 OpenAPI 和前端类型，减少手工维护两套结构。
- 每次新增 M3 工具必须同时提交权限规则、字段映射、失败行为和隔离测试。
- 每次新增渠道必须实现统一契约与重复消息测试，不复制一份业务权限逻辑。
- 提供安全的 .env.example、Docker 文件、README、数据字典和错误排查手册。
- 文档和测试产物保持可人工检查；真实凭据、真实客户订单不进入测试夹具。
- 保留原项目许可与第三方声明，明确记录改动；不直接在上游主线累计不可追踪修改。
- AI coding agent 在开发/测试环境工作，生产发布、权限扩大和数据库迁移经过人工审核。

## 17. 评审事项

建议先确认本稿的总体边界：渐进模块化、身份与权限归平台、ADP 保留编排、首个里程碑为官网+后台+M3 只读闭环。

后续逐项确认：

- 客户企业员工默认可见企业所有订单，还是还要按部门/经办人继续细分。
- 首个外部微信入口优先服务号还是微信客服，企微外部客户的具体使用形态。
- M3 实际 API 的企业归属字段、分页、限流、错误码、Token 生命周期和测试环境。
- 当前 ADP 应用模式下的工具参数与服务身份验证能力。
- 账号会话/渠道授权有效期、日志留存、备份与恢复目标。

本文只定义重构设计。未经后续明确授权，不修改 ADP 云端应用、渠道回调、M3 权限或当前运行配置。
